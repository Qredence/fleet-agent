# Taste
- Issues terse, imperative commands ("merge pr 13", "run backend", "test a POST query") and expects the agent to infer the target and act directly, without asking for clarification or restating the request. Confidence: 0.7
- Drives structured work through slash-commands/skills (/evo:discover, /evo:optimize, /evo:ship, /babysit-pr) rather than asking for step-by-step manual instructions. Confidence: 0.6
- For plan-first work (multi-issue remediation, refactors, simplifications), expects a written plan with explicit decision-point questions before execution begins — explicitly requests "Ask me questions" — each question presented as options plus a recommended choice. Confidence: 0.85
- Wants changes verified by real test runs, not typecheck alone; will scope fixing a broken test environment into the task so verification is meaningful. Expects a green baseline before changes and an identical re-run after, with exact results recorded, plus small mechanical probes to verify invariants rather than trusting code reading alone; when framework docs are ambiguous or conflict, verifies behavior by reading the installed library source before refactoring against it. Confidence: 0.75
- Prefers full one-time migrations over compatibility shims/deprecation layers; deletes dead code and unused API surface outright (e.g., re-export shims, barrel files with zero importers) rather than keeping permanent indirection; chose the aggressive full-deletion scope (~1,600 lines) when offered moderate/minimal simplification options. Confidence: 0.8
- YAGNI: avoids speculative complexity — won't introduce typed exceptions or extra abstraction for failure modes that don't exist yet. Confidence: 0.6
- Prefers framework-native implementation over homegrown layers: when the library documents a capability, delete the custom layer in its favor (declarative YAML spec compiler → direct `dspy.make_signature` construction, custom diagnostics transport → DSPy's own bounds, forced-submit compat shim → program-boundary handling); keep custom code only where the library genuinely can't serve the need (e.g., per-run BYOK engine ownership). Stated goal: backend "as light and simple as possible while keeping the native capabilities". Confidence: 0.75
- Ships finished work as pull requests: expects staged/uncommitted changes to be committed on a new feature branch and a PR opened (via `gh`), rather than committing directly to main. Confidence: 0.7
- Repo ship conventions: conventional commit messages (`refactor: ...`), type-prefixed descriptive branch names (`feat/`, `chore/`, `refactor/` — inferred by inspecting existing branches rather than asking), and a PR template with a validation checklist (lint, tests, build, ruff format, mypy, pytest) — run every check before opening the PR and explicitly explain any skipped checklist items rather than leaving them silently unchecked. Confidence: 0.6
- Gives bare git instructions ("commit and push") and expects the full workflow handled end-to-end without questions — check identity/branch state, stage, commit, push, then verify the remote outcome (e.g., confirm alerts/CI state). Confidence: 0.6
- Commit messages follow Conventional Commits (`chore(deps): ...`, `refactor: ...`) with a descriptive body explaining the what/why, ending in trailers: `Signed-off-by:` (repo enforces commit sign-off) and `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>`. Confidence: 0.6
- Stages only the intended paths explicitly, deliberately leaving agent/tooling directories (e.g., `.commandcode/`, `.hermes/`) out of the commit; keeps commits to the strictly scoped single deliverable and does not push unless asked. Confidence: 0.6
- Prefers code reviews run through the repo's team-standard review tooling (`chunk build-prompt` / the review prompt mined from GitHub PR history) rather than an ad-hoc review against generic engineering standards. Confidence: 0.5
- Hands off pre-authored plan files referenced via `@` (`.hermes/plans/`, timestamped names) with a terse "implement this plan" and expects the plan executed faithfully — its phases followed literally, tracked as a todo list, its fixed validation gates honored, and output scoped to the plan's single deliverable. Confidence: 0.75
- Major refactors are gated by a checked-in one-page spec written before code changes (problem, measured census table, invariants, contract impact, test-change ledger, acceptance criteria), with appendices filled after execution (probe recordings, line-delta ledger, commit list); dated snapshot docs (e.g., a prior review) get a one-line "addressed" cross-reference in place rather than being rewritten. Confidence: 0.65
- Grounds refactor scoping in a measured usage census before proposing options — line counts, importer greps, production-vs-test usage verdicts (via parallel explore subagents) — so every deletion candidate is quantified, not guessed. Confidence: 0.65
- Final validation mirrors CI exactly: reads the CI config and copies its precise commands (ruff/ruff format/mypy/deptry, migrations, pytest, uvicorn boot smoke) into the spec, then runs the same battery at the end. Confidence: 0.65
- Deliverable/review documents must be evidence-grounded: verbatim upstream-doc quotes with URL and access date, `file:line` refs for every repo claim, no invented URLs (each URL actually fetched during the session), and a validation appendix with exact commands and outputs. Confidence: 0.8
- Python repos use uv for env/dependency management (`uv sync --locked`, `uv run`) with pytest for tests; the app's `.env` is never sourced for test commands (env file overridden to /dev/null and explicit test-DB URL passed). Confidence: 0.6
