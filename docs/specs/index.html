Main conclusion

Fleet Agent does not need a new agent framework. It needs a stronger contract between what the UI offers, what the agent can actually do, what the server saves, and what the user sees after reload.

The proposal keeps one FastAPI application, PostgreSQL, native DSPy programs, AG-UI transport and assistant-ui. It does not introduce a generic workflow engine, arbitrary model-authored page layouts, or a new parallel frontend state store.

Six starter implementation specs accompany the review. They are proposals, not descriptions of implemented behavior.

01 - Architecture and verdict

Page index | Next: backend

Verdict

The foundation is substantially aligned with a DSPy-native, UI-first agent workbench. The next investment should be product correctness, not a framework migration.

The repository already implements the important separation between an internal agent program and its public workspace projection. It also records explicit engineering principles against speculative abstractions and against exposing hidden reasoning. Treat those principles as constraints on the next changes, not as documentation to replace.

Sources: AGENTS.md; README.md.

Current system

React workspace / assistant-ui
  | REST resources + AG-UI stream
FastAPI / live run coordinator
  | run-scoped engine; branch-aware history
FleetAgent (DSPy Module)
  | one selected capability profile
ReActV2 evidence gathering -> synthesis Predict
  | safe text / domain events / managed tool results
Public reducer -> snapshots, deltas, tool parts, CUSTOM cards
  |                          |
PostgreSQL + artifacts       React process panel + transcript

MLflow: optional operator-side tracing and offline evaluation history

The frontend uses React, Vite, assistant-ui and the AG-UI integration. The backend pins DSPy 3.4.0 and MLflow 3.16.1. PostgreSQL stores threads, branches, safe process state and server-side continuation history. Do not confuse the private continuation history with the browser-visible process summary.

Sources: apps/web/package.json; apps/api/pyproject.toml; apps/web/src/features/agent-runtime/agent-runtime-provider.tsx; apps/api/app/agent/program.py; apps/api/app/persistence/run_persistence.py.

Boundaries worth keeping

Native DSPy composition. FleetAgent is a dspy.Module; routing is a predictor; profile-specific ReActV2 loops gather evidence; a separate synthesis predictor streams explicit public fields. This is already a sensible DSPy design. There is no reason to replace it with a competing orchestration framework.

Deterministic tool exposure. build_tool_profiles() filters approval-gated tools before constructing the program. Preserve that order. A model's confidence in a requested action is not a permission grant.

A safe public projection. The engine scrubs streamed public text, the mapper emits AG-UI events, and the workspace schema excludes arbitrary properties. The browser does not need to know DSPy history objects or next_thought.

Branch-aware persistence. Reservation and lifecycle changes use short transactions; continuation history is chosen by branch ancestry. Improve failure semantics without discarding this infrastructure.

Explicit frontend ownership. Keep REST resources in React Query, execution/process state in AG-UI, and local layout preferences in Zustand. The process panel already follows the latter separation.

Sources: apps/api/app/agent/program.py; apps/api/app/agent/factory.py; apps/api/app/agent/approval.py; apps/api/app/agent/engine.py; packages/contracts/agent-workspace-state.schema.json; apps/api/app/persistence/run_persistence.py; apps/web/src/features/process-panel/process-panel.tsx; AGENTS.md.

Where the architecture currently breaks down

Some individually reasonable parts do not yet compose into one honest product contract. A report profile can create an artifact but cannot inspect workspace files; a workspace profile can inspect files but cannot create the managed report. The attachment UI accepts images while the execution boundary extracts text only. Successful streaming can be reported even after terminal persistence fails. Feedback is session-local.

These are better priorities than adding more components, more graph nodes, or more model calls.

Sources: apps/api/app/agent/factory.py; apps/api/app/agent/program.py; apps/web/src/features/agent-runtime/agent-runtime-provider.tsx; apps/api/app/kernel/run_input.py; apps/api/app/agui/live_coordinator.py.

Recommended target

Keep the current deployment topology. Make the application flow explicit:

Validated user request + selected branch + input capabilities
    -> requested task / output intent
    -> deterministic permissions and available tools
    -> native DSPy evidence gathering
    -> bounded, source-addressable evidence
    -> native DSPy synthesis
    -> optional authorized managed artifact export
    -> safe public result + durable settlement
    -> consistent live and restored UI

This is a proposal, not an additional generic framework. Most of it can be implemented by clarifying existing functions and ordinary data types. In particular, managed report creation should be an output stage rather than a mutually exclusive alternative to workspace evidence gathering.

Keep latency, cost and observability proportional to the task. Do not add Jev, a second critic, a planner or an optimizer call to every interaction merely because the library exposes it.

Deployment boundary

The README identifies the product as a single-local-owner application rather than a multi-user authorization system. Before deploying it as a shared hosted service, make authenticated principals, object-level project/thread/artifact access, credential handling, execution isolation and server-owned authorization explicit release gates. This is a deployment recommendation, not a claim that an exploit was demonstrated.

Sources: README.md; apps/api/app/agent/approval.py.

02 - Backend and reliability

Page index | Next: frontend

F01 - Compound tasks are blocked by the profile shape

Confirmed. build_tool_profiles() gives artifact the research capabilities plus artifact creation. Workspace profiles contain research and workspace capabilities but omit artifact creation. FleetAgent.forward() selects exactly one route. Therefore no selected profile can both inspect workspace files and invoke the managed-report tool in the same run.

A minimal regression case is: "Inspect the workspace implementation and create a managed report explaining the findings." Evaluating either half separately will miss the defect.

Recommendation: keep evidence routing, add an explicit managed-output intent, and execute managed report export after evidence collection and synthesis using the existing bounded storage/tool boundary. Recheck authorization before export; use stable run/artifact identifiers to avoid duplicate writes on retries. A narrowly scoped combined profile is an acceptable tactical fix, but avoid expanding into a powerset of profile names.

Sources: apps/api/app/agent/factory.py; apps/api/app/agent/program.py.

F03 - Completion and successful saving are different facts

Confirmed. In the successful coordinator branch, answer/state events are sent, persistence is retried, and a failed settlement is logged. The stream still emits RunFinishedEvent. The execution may have completed, but the answer has not necessarily been saved for restoration.

Recommendation: distinguish execution outcome from persistence status. Proposed statuses such as saveStatus: pending | saved | failed should be versioned in the shared contract. Stream the useful answer immediately; only show "Saved" after a successful transaction. On save failure, keep the answer visible with an explicit warning and a safe copy/export option. Do not promise recovery of data that was never persisted.

Preserve the existing short transaction boundaries. Before introducing an event log, queue or outbox, establish the actual required guarantee. An outbox can improve reliable event publication after a commit; it cannot make an unavailable database accept the original commit.

Test failures on both settlement attempts, cancellation during settlement, duplicate finish attempts, and reload after each outcome. A terminal transport event is not proof of exactly-once processing of every tool side effect.

Sources: apps/api/app/agui/live_coordinator.py; apps/api/app/persistence/run_persistence.py.

F04/F05/F06 - Grounded answers need preserved context and evidence status

Three source-level issues interact:

  1. The router receives only user_request, even though the program has branch history. Follow-ups such as "turn that into a report" cannot be routed from the referenced context.
  2. _evidence_json() walks the accumulated history in order. bounded_json() retains a budget-limited prefix and shortens the overflowing entry. Old observations can therefore consume the budget before a newly collected correction is included.
  3. The final prediction always sets termination_reason="synthesis", discarding the gatherer's termination reason. A syntactically valid final answer is not proof that evidence gathering completed.

Recommendation: route with a bounded branch-local summary and explicit available capabilities. Separate route validity from fallback selection. Prioritize current-turn observations plus older evidence explicitly referenced by the user; preserve source IDs, tool-call IDs and truncation indicators. Carry the gatherer outcome through to the final result and UI.

Do not convert every abnormal gatherer exit into total failure: a partial answer can be valuable. Its status and caveats must be truthful and grounded in retained evidence. Conversely, do not turn a router parse error into a confident unsupported answer simply because direct exposes no privileged tools.

Sources: apps/api/app/agent/program.py; apps/api/app/agent/routing.py; apps/api/app/agent/evidence.py; apps/api/app/agent/engine.py.

F09/F10 - Reduce avoidable DSPy runtime coupling

Confirmed implementation; concurrency impact not reproduced. build_synthesizer() is globally cached and returns a mutable DSPy Module reused across otherwise run-scoped programs. Cache immutable specs or prompt definitions, not live predictors, unless a concurrent isolation test proves the selected sharing strategy safe.

The engine also patches the private _forced_submit method and extracts reasons from exception text. Keep any unavoidable workaround in one explicit, pinned compatibility module with contract tests and a deletion condition. Prefer supported return and exception semantics; do not fork ReActV2 again.

Tests should interleave two runs with different providers, histories and cancellation signals. Assert no cross-run stream routing, configuration mutation, usage attribution or history contamination. No cross-run data leak was demonstrated in this review.

Sources: apps/api/app/agent/signature.py; apps/api/app/agent/engine.py; apps/api/app/agent/factory.py.

Cancellation and scheduling

The inspected execution path offloads synchronous programs to worker threads and uses a cancellation token and shielded cleanup. Do not describe cancellation as immediate thread termination. Decide explicitly whether closing a stream cancels the run or merely detaches the client; the current coordinator attempts cancellation on disconnect.

For the next release, retain this simple connection-coupled model and make cancellation status honest. A background worker becomes justified only when the product requires durable detached jobs, reconnectable execution or independent scheduling. Native async conversion should be measured against the locked DSPy version, not treated as an automatic rewrite.

Sources: apps/api/app/agent/engine.py; apps/api/app/agui/live_coordinator.py.

Organization: move only when a boundary becomes clearer

Keep agent-specific DSPy construction in agent/, shared public schemas in packages/contracts, persistence in its current boundary, and AG-UI serialization in agui/. When modifying lifecycle behavior, extract only the terminal-settlement policy from the large coordinator into a small application-level unit. Avoid creating parallel service/repository/manager layers for each function.

The ideal acceptance criterion is not a smaller file count or a prescribed directory tree. It is that lifecycle behavior can be tested without serializing SSE, and transport changes cannot accidentally redefine business outcomes.

03 - Frontend and public contracts

Page index | Next: DSPy and evaluation

Keep the existing interaction model

The existing runtime integrates HttpAgent, useAgUiRuntime, a thread-history adapter, inline Data UI registrations and a process panel. Keep that architecture. The goal is a dependable conversation-first workspace, not a mandatory DAG viewer or a model-controlled application shell.

The following recommendations come from source inspection, not a rendered screenshot audit. No claims about measured rendering performance, accessibility conformance or visual defects are made.

Sources: apps/web/src/features/agent-runtime/agent-runtime-provider.tsx; apps/web/src/features/agent-runtime/inline-agent-data-ui.tsx; apps/web/src/features/process-panel/process-panel.tsx.

F02 - Do not offer inputs the agent cannot use

The frontend registers image and text attachment adapters. The backend request extractor handles text strings and text parts only. An image preview is therefore not evidence that the DSPy program received an image.

First fix: expose accepted modalities and size limits through the existing capabilities contract. Until end-to-end image handling is implemented, hide image attachment controls and reject unsupported image input at the server with a stable public error. Never silently ignore it.

Later feature: support typed image/document inputs through validation, storage, authorized retrieval, DSPy input conversion and thread restoration. Include mixed text-plus-image and image-only cases in tests. This is more than an upload endpoint.

Sources: apps/web/src/features/agent-runtime/agent-runtime-provider.tsx; apps/api/app/kernel/run_input.py.

Make the run state legible

Use a compact run-status component above or beside the answer. It should explain the state that affects the user's next action: working, waiting for a pre-run permission choice, partial result, completed, cancelled, failed, or completed but not saved. Detailed tool activity belongs in the inspector, not in the user's way.

Treat execution status, evidence sufficiency and save status as separate facts. For example, "Answer completed; saving failed" is more accurate than either "Everything failed" or an unqualified success chip. Display safe error text and run ID, with a relevant retry/copy action, rather than relying on console logging.

This requires an explicit schema change; the current public schema is version 1 and forbids unknown properties. Regenerate Python and TypeScript types and provide an explicit bootstrap migration for older snapshots.

Sources: apps/web/src/features/agent-runtime/agent-runtime-provider.tsx; packages/contracts/agent-workspace-state.schema.json; apps/api/app/agui/live_coordinator.py.

Approval: retain the simpler pre-run decision

The backend accepts forwardedProps.approvedTools and withholds gated tools before construction. The reviewed runtime provider does not set this property; repository search found it in backend code, documentation and tests, not a frontend sender. Treat a usable frontend approval path as a gap to confirm during implementation.

Add a narrow pre-run permission control with named tools and an explicit scope, using the existing tool metadata as the source of truth. Default to none; avoid a casual "approve all" control. Starting a fresh authorized run is preferable to reviving the previous private-DSPy pause/resume fork.

For a multi-user deployment, the request is only a requested approval selection. Intersect it with server-owned permissions for the authenticated principal. A browser boolean or model probability is not authorization.

Sources: apps/api/app/agent/approval.py; apps/web/src/features/agent-runtime/agent-runtime-provider.tsx; apps/api/app/agent/factory.py.

F08 - Bounded dynamic composition, not generated React

The repository already registers agent-progress, web-search, sources, research-report and artifact cards. Do not introduce a second generative UI transport. The gap is that the inline payload parsers and versions are handwritten locally while the main process state is schema-generated.

Proposed direction: a closed, versioned union of safe presentation payloads, generated from packages/contracts, mapped through a small static React renderer registry. Begin by formalizing the existing cards; add a new card only for a demonstrated task outcome.

Useful future kinds include a comparison table, approval request, structured findings, or artifact preview. The model may choose from allowed presentation kinds and bounded data; application code retains navigation, pane arrangement, authentication and executable behavior.

Unknown versions or malformed payloads must leave the surrounding answer usable with a safe fallback. Use real source IDs that resolve to authorized source records; do not manufacture links from model-provided titles. Clamp numeric indices and collection sizes, and validate finite numbers.

Sources: apps/web/src/features/agent-runtime/inline-agent-data-ui.tsx; apps/api/app/agui/event_mapper.py; packages/contracts/agent-workspace-state.schema.json; AGENTS.md.

One public fact, several views

Derive transcript cards and the inspector from the same safe projection and stable IDs. A source shown in a card should resolve to the same record in the Sources tab. Avoid a separate mutable mirror of execution state in Zustand.

Test historical progress during a new run: the inline search renderer currently consults thread-wide isRunning. A historical unfinished marker should not become active merely because another run has started. Use message/run identity when deciding live versus settled rendering.

For durable cards, define how the bootstrap contains their settled representation; transient CUSTOM delivery alone is not a durability guarantee. Live rendering, branch selection and reload must converge on the same user-visible result.

Sources: apps/web/src/features/agent-runtime/inline-agent-data-ui.tsx; apps/web/src/features/process-panel/process-panel.tsx; apps/web/src/features/agent-runtime/agent-runtime-provider.tsx.

F07 - Turn feedback into a useful product signal

The current feedback adapter writes to an in-memory Map. Persist feedback by message and run, with an optional bounded reason and a recorded program version. Confirm persistence in the UI and restore the selected state on reload.

Do not automatically feed every positive response into training. Create a reviewed, redacted candidate pool; add task labels and expected evidence; deduplicate by thread/task; keep evaluation holdouts separate. Feedback is supervision to curate, not automatic ground truth.

Sources: apps/web/src/features/agent-runtime/agent-runtime-provider.tsx.

Performance and usability gates

Add fixture-based browser journeys for text-only use, denied permissions, partial results, save failures, cancellation, branch switching, artifact restoration and malformed cards. Test keyboard focus, status announcements, small-screen inspector access and reduced motion.

Profile long transcripts and high-frequency token streams before adding selectors, memoization or virtualization. The recommendation is to measure and then optimize the affected boundary, not to install another state library.

04 - DSPy, evaluation and MLflow

Page index | Next: delivery

Use DSPy more directly, not more abstractly

Fleet Agent already uses native Modules, Predictors, ReActV2 and streaming. Keep that. The runtime YAML layer, however, defines its own field registry, module vocabulary and graph validation, while important control flow and evidence transformation remain in Python.

Recommendation: distinguish requirements specs from a runtime programming language. Keep Markdown prompts where readable; prefer ordinary typed DSPy Signatures and a small FleetAgent Module. Retain YAML only for configuration that has a real authoring requirement. Before deleting the dialect, inventory callers and tests; remove unused composite/generalization features rather than breaking needed behavior indiscriminately.

AGENTS.md asks for specs under docs/specs/, but that directory was absent in the reviewed docs listing. The supplied specs make the intended product behavior explicit without requiring a new agent DSL.

Sources: AGENTS.md; apps/api/app/agent/program.py; apps/api/app/agent/signature.py; apps/api/app/agent/spec/schema.py.

F11 - Fix the metric before optimizing it

The routing metric returns 1 for exact match, 0.35 for a route with a higher numeric rank, and 0 otherwise. The optimizer calls its threshold min_accuracy, but this is a weighted utility, not exact-match accuracy.

More importantly, capabilities are not totally ordered. An artifact route has report-generation capability that a numerically higher workspace route lacks. Giving that workspace prediction partial credit for simply being "more capable" misdescribes the executable tool set. Also, coercing malformed predictions to direct can conceal invalid output on direct-labeled examples.

Recommendation: report exact route match, invalid-output rate, task/capability sufficiency and unnecessary tool exposure separately. Derive sufficiency from actual capability sets. Keep unauthorized-tool exposure/execution as a hard test invariant, not a penalty a quality score can compensate for.

Add compound tasks, follow-up references, unavailable tools, denied approvals, malformed decisions, provider errors, long evidence histories and partial gatherer exits to evaluation cases. Score end-to-end success as well as the isolated router.

Sources: apps/api/evals/agent_tool_routing.py; apps/api/app/agent/factory.py; apps/api/app/agent/routing.py; apps/api/evals/optimize.py.

Preserve the good promotion boundary

The current optimizer scores a baseline and candidate on a held-out split and does not pass that split into GEPA. It rejects unchanged instructions and requires explicit activation. Keep those protections.

GEPA currently uses the same training set for candidate construction and selection (trainset=train, valset=train). As the dataset grows, separate train, development selection and final promotion holdout by task/thread/repository rather than randomly splitting near-duplicate paraphrases. Do not repeatedly use the final holdout to choose among manual iterations and still call it untouched.

Define hard release gates: no safety regressions; no unsupported success claims; task-quality improvement on held-out examples; and an acceptable latency/token budget. Report provider failures separately from reasoning errors. No baseline or improved score was measured during this review.

Sources: apps/api/evals/optimize.py; apps/api/evals/agent_tool_routing.py.

Jev and ReAnchor: useful, but not the next dependency of every run

Official DSPy documentation identifies Jev decision types and ReAnchor as experimental. Choice supports discrete decisions; Noul supports boolean decisions. ReAnchor tunes numeric decision settings rather than rewriting prompt instructions. Keep these types inside a narrow internal boundary and expose ordinary domain values to the rest of Fleet Agent.

Official references: jev; reanchor.

My recommended experiment is bounded: compare the existing predictor with a decision-typed capability selector, or test an evidence-sufficiency decision on labeled cases. Do not add both immediately. Choose the one that produces the clearest measured product improvement.

Define an ordinary internal result, conceptually:

CapabilityDecision(selected, valid, fallback_reason)
EvidenceAssessment(status, missing_requirements, evidence_ids)

These are proposed application types, not public DSPy types. Deterministic code still computes the allowed tools and controls actions. A confidence value is never a grant, and a model-produced probability is not automatically an empirically calibrated reliability estimate.

Use separate development/calibration and final holdout data. Compare task success, false-sufficient decisions, parse failures, latency and request cost. Keep a baseline fallback and pin the experiment's model, program and dependency versions. Promote only after the UI correctly distinguishes partial and insufficient evidence.

F12 - Extend MLflow, do not add it from scratch

MLflow integration already exists. Startup tracing is opt-in and degrades on configuration failure. Offline routing/evaluation attempts already log metrics and selected metadata. Rejected optimization attempts, however, generally lack the candidate configuration and report because artifact directories are only written for passing candidates.

For every completed attempt, save a bounded candidate artifact, report and manifest regardless of outcome. Record the git revision, task model, relevant model settings, DSPy version, prompt/program fingerprint, dataset digest, split IDs, baseline/candidate metrics, failure counts and promotion decision. Avoid logging credentials or user secrets in manifests.

Tie the safe application run ID to operator traces, without exposing provider prompts or private reasoning to the browser. Keep tracing off the critical path; an unavailable MLflow store must not decide whether a runtime result exists.

Sources: apps/api/app/services/mlflow_observability.py; apps/api/evals/mlflow_tracking.py; apps/api/evals/optimize.py.

Make trace privacy explicit

The live tracing module intentionally captures prompts/completions in the operator store and scrubs secret-shaped values. That is not the same as a policy to exclude private reasoning or all sensitive user content. Reconcile this with the stricter engineering guidance.

Use metadata-only telemetry as the normal operational baseline. Any detailed diagnostic capture should be separately enabled, access-controlled, redacted, retention-limited and documented. Test nested payloads and failure paths. Do not claim a secret leak based only on the existence of autologging; none was demonstrated here.

Sources: apps/api/app/services/mlflow_observability.py; AGENTS.md.

05 - Prioritized delivery plan

Page index | Next: evidence

Delivery principle

One focused product behavior per task/Orb. Each change must state its public contract impact, frontend behavior, fixture behavior and evaluation impact. Prefer an end-to-end vertical slice to a backend-only feature with no usable UI.

This plan has no time estimates and does not imply that any implementation has been performed.

Recommended sequence

Order Focused change Completion evidence
1 Supported inputs and honest saved/unsaved status Unsupported modalities fail visibly; database failure cannot appear saved; reload reflects the durable record.
2 Compound workspace-to-report task One request inspects actual workspace files and returns one managed artifact, with no unauthorized tools.
3 Evidence continuity and stage outcomes Follow-ups route with branch context; current observations survive history truncation; partial gathering remains visible after synthesis.
4 Shared inline-card contract and approval UX Generated types/validation; safe unknown-card fallback; pre-run approval sent explicitly; live/reload agreement.
5 Persistent feedback and corrected eval metrics Feedback survives reload; exact-match and capability utility are distinct; grouped holdout and failure reporting exist.
6 DSPy simplification and optional Jev experiment Run-isolated predictors; narrower compatibility shim; measured experimental improvement before activation.

Steps 1-3 fix user-visible correctness. Steps 4-5 close the product/evaluation loop. Step 6 should not block those fixes. The six supplied specs separate these concerns more precisely for implementation.

Required release gates

Contract gate: regenerate Python and TypeScript; validate representative snapshots and CUSTOM payloads; explicitly migrate existing persisted snapshots when the schema changes.

Safety gate: gated tools are absent from unauthorized programs; malformed routing does not expand permissions; streamed and final public output remain scrubbed; private reasoning never enters browser contracts.

Product gate: request, stream, terminal state, branch selection and reload agree. Failures have useful UI outcomes rather than only logs. Fixture mode remains deterministic.

Evaluation gate: when agent behavior changes, record a baseline on fixed examples, then a candidate comparison. Keep held-out promotion examples out of optimizer selection. Do not trade away safety or persistence truthfulness for a higher mean score.

Sources: AGENTS.md; packages/contracts/agent-workspace-state.schema.json; apps/api/app/agent/approval.py; apps/api/app/agent/engine.py; apps/api/evals/optimize.py.

CI: add integration, not more isolated green checks

The inspected CircleCI workflow already configures web audit/lint/Vitest/build, backend audit/lint/types/migrations/pytest, a real API boot smoke and a schema-validation job. These are strengths. The shown workflow does not invoke the repository's fixture browser E2E script, and the web test script is Vitest.

Add a deterministic full-stack browser job using the existing fixture path, covering the release gates above. Verify generated contract freshness in both languages as an explicit gate, extending existing tests rather than assuming there are none. Keep provider-backed smoke/evaluation opt-in or in a controlled environment with budgets.

Sources: .circleci/config.yml; apps/web/package.json; README.md.

Reusable Amp Orb task instruction

Read AGENTS.md and the relevant docs/specs/ file before editing.
Inspect the current implementation and identify the smallest end-to-end change.
Do not add a framework, another frontend state owner, or a private DSPy loop fork.
Preserve deterministic authorization, safe streaming, branch semantics and fixtures.

Implement one specification's acceptance criteria only.
Update shared schemas and generated models when the public contract changes.
Include the matching frontend state and a deterministic browser scenario.
For behavior changes, compare the baseline and candidate on fixed eval examples.

Report: files changed, observable behavior changed, contract/migration changes,
UI/fixture impact, commands actually executed, measured results and limitations.
Do not report unexecuted tests or proposed scores as passing evidence.

What not to add now

Do not add a distributed job platform, a general agent graph language, a second generative UI protocol, autonomous online self-optimization, arbitrary model-defined layouts, or a parallel execution-state store. Revisit these only when a specific product requirement cannot be met with the current stack.

Spec 001 - Run outcome and durability

Status: proposed, not implemented. Baseline: 8b87cafc25a887b4b144df4ad938f47652d20866.

Specification index | Review pages

Problem and current behavior

A completed answer can be streamed even when both terminal persistence attempts fail. The coordinator logs the failure and emits RunFinishedEvent. Execution completion and durable save success are not the same guarantee.

Source: live_coordinator.py, successful terminal branch; run_persistence.py.

Desired behavior

Keep useful streaming output visible. Explicitly distinguish the execution outcome from whether that output was saved. Show "Saved" only after the terminal transaction commits. A failed save must remain visible in the current browser session, with an explanation that reload may not recover the answer.

Invariants

  • Exactly one logical terminal transition is accepted for a run; repeated settlement cannot produce duplicate assistant messages or artifacts.
  • Public output remains scrubbed. Never expose driver errors, provider payloads or private history.
  • A successful stream is not described as durable until persistence succeeds.
  • A save failure does not erase already delivered useful text or trigger an automatic re-execution of mutating tools.
  • Closing a connection retains the explicitly documented cancel-on-disconnect behavior for this slice.

Contract and migration

Propose a shared versioned run field saveStatus: pending | saved | failed, independent from the existing execution status. Define a stable public save-failure code. Decide the version increment in the schema PR; version-1 records require an explicit normalization/migration path because the existing schema forbids unknown properties.

Use the existing AG-UI state snapshot/delta and terminal events. Do not invent a parallel transport. The persisted terminal state may contain its intended saved value inside the transaction, but the client receives that value only after commit succeeds. On commit failure, emit a safe unsaved state for the current session.

Backend and frontend

Extract only enough settlement policy to test it independently from SSE serialization. Keep the existing short transactions and branch/message identifiers. The frontend run banner must distinguish working, execution complete, and save failure, while retaining copy/download access to the visible answer where safe.

DSPy, MLflow and fixtures

No DSPy optimization is needed. Record sanitized settlement outcome/count metrics; MLflow availability must not affect settlement. Add deterministic fixtures for successful save, retry success, both retries failing and cancellation during save.

Acceptance tests

  1. Successful commit produces one saved answer and the same answer after reload.
  2. First persistence attempt fails, second succeeds: no duplicate message and no false permanent failure.
  3. Both attempts fail: answer remains visible, UI says not saved, and bootstrap does not invent a persisted answer.
  4. Duplicate finalization and disconnect races produce no contradictory saved/failed states.
  5. A save retry never reruns the DSPy program or a workspace mutation.
  6. Old snapshots normalize predictably; live and restored terminal state agree whenever a terminal transaction succeeded.

Non-goals

No background-job platform, token-by-token event log, unbounded retry queue, or promise to recover data that was never saved.

Spec 002 - Compound tasks and managed output

Status: proposed, not implemented. Baseline: 8b87cafc25a887b4b144df4ad938f47652d20866.

Specification index | Review pages

Problem and current behavior

artifact exposes research and report creation. Workspace profiles expose research and workspace tools, but not report creation. The program selects exactly one profile. A task needing workspace evidence plus a managed report cannot access both through the current composition.

Sources: factory.py, build_tool_profiles; program.py, forward.

Desired behavior

A user can request "Inspect the workspace and create a managed report" as one task. Evidence gathering uses the minimum authorized workspace profile; managed report export is a separately authorized output action after synthesis. The report cites the evidence actually gathered.

Invariants

  • Requested capabilities, configured availability and authorization remain distinct.
  • Only deterministic application policy decides which tools/actions may execute.
  • Denying workspace writes or shell access must not prevent a read-only inspection and allowed managed export.
  • A report cannot claim a source was inspected when it was not.
  • Retried delivery/export must not duplicate artifact records or silently overwrite unrelated artifacts.

Minimal design

Retain evidence routing and add a bounded output intent, rather than introducing a generic planner or every possible profile combination. Reuse the existing report storage, validation and event machinery outside the mutually exclusive evidence choice. Synthesis can supply report content from the same evidence; avoid an extra LM call when the answer already contains the report.

A tactical combined profile is permitted only as a small documented step with the same tests. Do not expand route rank assumptions into authorization logic.

Contract and frontend

Represent managed-output request/status through the existing artifact lifecycle, extending generated contracts only where needed. Return stable artifact and source references. The transcript shows artifact progress/ready/failed; the inspector and restored branch refer to the same record.

DSPy evaluation

Add deterministic tool doubles for read-only workspace inspection, research plus report, missing required tool, denied mutations and export failure after a useful answer. Update capability sufficiency scoring to use actual sets. Exact route match, task success and authorization invariants are separate measurements.

MLflow and fixtures

Record selected evidence profile, requested output kind, export status and program version as safe metadata. Fixture scenarios must exercise combined capabilities rather than merely show a prebuilt artifact card.

Acceptance tests

  1. One task reads known workspace content and produces one managed artifact containing the expected grounded finding.
  2. No write/edit/bash tool is exposed when not approved.
  3. An unavailable evidence capability yields a clear limitation, not fabricated inspection.
  4. A follow-up "make that a report" uses the correct branch evidence.
  5. Export failure keeps the answer, marks the artifact failed and never shows a ready download.
  6. Repeated export settlement is idempotent for the same run/output identity.
  7. Reload and branch switching preserve the correct report and source associations.

Non-goals

No arbitrary generated agent graph, no new artifact service, no automatic permission escalation.

Spec 003 - Evidence continuity and outcome

Status: proposed, not implemented. Baseline: 8b87cafc25a887b4b144df4ad938f47652d20866.

Specification index | Review pages

Problem and current behavior

Routing sees only current request text. Evidence is serialized from accumulated history into a bounded prefix. The final prediction labels termination as synthesis, without preserving the gatherer reason. These choices can make follow-ups under-specified, omit current corrections and hide partial evidence collection.

Sources: program.py, evidence.py, engine.py.

Desired behavior

Routing receives bounded, branch-local conversational context. Synthesis receives current relevant observations plus explicitly needed prior evidence. The result distinguishes successful synthesis from complete, partial or insufficient evidence gathering.

Invariants

  • Private DSPy history remains server-side; public explanations are deliberately written summaries.
  • Current corrective evidence cannot be crowded out solely because older observations filled the budget first.
  • Evidence JSON is always valid and bounded; preserve the existing valid-JSON guarantee.
  • Invalid routing remains permission-safe and retains a diagnostic/degraded signal.
  • Gatherer failures cannot disappear merely because a synthesis call returns valid text.

Minimal implementation

Pass a bounded conversation summary or recent relevant turns into the routing signature. Separate raw decision validity from the coerced fallback route. Partition current-run observations from older history before selecting evidence; preserve stable source/tool-call IDs and a deterministic truncation record. Avoid a vector database or another agent for this first iteration.

Carry a plain application-level evidence outcome and original normalized stop reason through AgentRunResult. Define when to synthesize a partial answer and when to return an insufficiency explanation. A future model-based sufficiency checker must not replace deterministic error and authorization handling.

Contract and frontend

Version the public quality/limitation fields using the shared schema. The answer and run banner disclose partial or insufficient evidence without showing raw exception messages or internal thoughts. Source references resolve to records accessible in the selected branch.

DSPy and evaluation

Use controlled histories containing old claims and newer corrections. Include request-only versus contextual routing comparisons, parse-error fallback and forced-stop cases. Report omission of required evidence, unsupported success claims, task completion, tokens and latency. Any improvement claim must be measured against the old implementation on the same cases.

MLflow and fixtures

Log evidence selection counts, truncation status, normalized outcome and version metadata. Do not log raw user documents or hidden history by default. Create fixtures for a follow-up, a correction near the budget boundary, and a partial result.

Acceptance tests

  1. "Use the newer file, not the old result" includes the newer evidence even after a long history.
  2. "Create a report from that" resolves the selected branch, not a sibling branch.
  3. Budget-boundary outputs parse as JSON and retain stable evidence attribution.
  4. A malformed router result never grants additional tools and never implies successful external verification.
  5. A gatherer max-iteration/context/parse stop remains observable after synthesis.
  6. Streamed and restored caveats agree, with no private reasoning in either surface.

Non-goals

No automatic long-term memory store, unbounded history, or universal second-model critic.

Spec 004 - Honest UI capabilities and shared cards

Status: proposed, not implemented. Baseline: 8b87cafc25a887b4b144df4ad938f47652d20866.

Specification index | Review pages

Problem and current behavior

Image attachments are offered by the runtime, but the execution extractor handles text only. Inline Data UI payloads have local handwritten parsers. Approval is supported at the backend boundary, but a frontend sender was not found in the inspected runtime/search results.

Sources: runtime provider, input extraction, inline cards, approval.

Desired behavior and delivery slices

A. Advertise and enforce supported input modalities. Ship this first.

B. Add an explicit pre-run permission selection using the existing tool metadata and request property. Verify the full UI sender path before changing it.

C. Formalize the existing inline cards as bounded, versioned shared contracts; do not add new card kinds in the same change.

Each slice should be a separate reviewable PR with its own browser test.

Invariants

  • The UI does not imply an unsupported image reached the agent.
  • Server validation remains authoritative even when the UI hides unsupported controls.
  • Approval defaults to none, is explicit for the current run, and never comes from model confidence.
  • The model cannot define arbitrary React, JavaScript, navigation or authentication behavior.
  • Process state remains in AG-UI; layout state remains local; no new mutable execution-state mirror is introduced.

Contracts

Extend the capabilities schema for accepted content types and limits. Add a closed discriminated schema for existing Data UI kinds, with stable entity/run/message references, version, bounded data and safe fallback semantics. Generate backend/frontend types and runtime validation using the established tooling.

Define which card state is durable in bootstrap. Prefer stable references into the authoritative public projection; transient events alone are not restored state. Provide migrations for older serialized card/snapshot versions.

Frontend behavior

Use the existing assistant-ui registrations and ordinary React components. Unsupported inputs are hidden or explained before submission. An unknown card version does not break the answer. Source selections open the corresponding authorized inspector record. Historical activity does not restart when a newer run is active.

Pre-run approval lists named capabilities and warns about mutations. Hosted deployments must intersect the selection with server-owned principal permissions; the existing single-local-owner model must not be silently generalized.

DSPy, MLflow and tests

No optimizer is required for the UI contract itself. Track safe schema rejection codes, not raw malformed payloads. Add fixtures for image rejection, denied approval, malformed and future-version cards, stable source linking and restored activity.

Acceptance tests

  1. Image-only and mixed unsupported inputs yield a visible stable error; no silent text-only substitution.
  2. Denied tools are absent from the constructed program, including after a malformed approval request.
  3. All current card fixtures validate against generated contracts in Python and TypeScript.
  4. Unknown kinds/versions preserve the answer and show a safe fallback.
  5. Old completed-run cards remain settled while a new run is active.
  6. Live, reloaded and branch-selected views reference the same sources/artifacts.
  7. Keyboard focus, status announcements and small-screen inspector access work in the fixture browser journey.

Non-goals

No second UI protocol, arbitrary model-generated page layout or private DSPy pause/resume fork.

Spec 005 - Feedback and evaluation provenance

Status: proposed, not implemented. Baseline: 8b87cafc25a887b4b144df4ad938f47652d20866.

Specification index | Review pages

Problem and current behavior

Feedback is stored in memory only. Routing utility is exposed as accuracy and uses numeric route rank despite non-nested capabilities. Failed optimization gates record metrics but generally not the full candidate report/configuration.

Sources: runtime provider, routing metric, optimizer, tracking.

Desired behavior

Persist useful user feedback and curate it into versioned examples. Evaluate exact prediction correctness, actual task sufficiency and safety separately. Keep a reproducible report for every completed optimizer attempt without auto-promoting it.

Invariants

  • Feedback is tied to the correct message, run and branch; retries do not create accidental duplicates.
  • User feedback is not automatically labeled ground truth or sent to an optimizer.
  • Invalid route output is counted as invalid rather than silently rewarded after coercion.
  • Required capability containment is checked against real tool metadata, not an assumed total order.
  • Promotion holdout examples never enter optimizer training or selection.
  • Evaluation and MLflow failures cannot authorize live changes.

Contracts and frontend

Add a small authenticated/owner-scoped feedback API and persisted record with bounded optional reason, message/run identity, and program version. Restore feedback on bootstrap or resource fetch and surface save failure. Use existing REST state ownership; do not place evaluation state inside the live AG-UI execution store.

Use explicit metric names: exact match, invalid-output rate, capability sufficiency, over-selection and task success. Retain weighted utility only under that name. Treat unauthorized exposure/execution as a hard test failure.

Dataset and optimization changes

Add compound and multi-turn cases first. Split by task/thread/repository to avoid near-duplicate leakage. Introduce train/development/final promotion separation when the expanded dataset supports it; retain the current held-out isolation until then.

Every completed optimization attempt writes a bounded manifest, candidate configuration, report and failure summary. Include git revision, model/config identity, DSPy version, program fingerprint, dataset digest and split IDs. Log passing and rejected attempts to the existing MLflow experiments; an unavailable tracker must leave local reports usable.

Trace privacy

Operational metadata is the default. Detailed prompt/completion traces require separately documented opt-in, access control, redaction and retention. Do not expose raw trace payloads through the frontend or attach secrets to candidate manifests.

Acceptance tests

  1. Feedback survives reload and remains attached to the intended branch/message.
  2. Feedback retry/update is idempotent for the chosen record identity.
  3. An artifact-required case predicted as workspace-only is correctly marked insufficient.
  4. Malformed predictions are reported separately and cannot receive exact-match credit through fallback coercion.
  5. Failed promotion gates still retain the candidate manifest and report.
  6. A corrupted or incompatible activated artifact is rejected with an operator-readable error.
  7. A deliberately failing safety case blocks promotion regardless of the mean quality score.
  8. MLflow outage does not delete the local evaluation report or change live behavior.

Non-goals

No autonomous online self-training, feedback-as-truth shortcut, or new observability platform.

Spec 006 - DSPy runtime simplification and optional decisions

Status: proposed, not implemented. Baseline: 8b87cafc25a887b4b144df4ad938f47652d20866.

Specification index | Review pages

Problem and current behavior

The synthesizer builder returns a cached mutable Module shared by run-scoped programs. The engine patches private forced-submit behavior. A custom YAML module dialect duplicates some native DSPy structure while routing and evidence transformation remain in Python.

Sources: signature.py, engine.py, spec schema.

Desired behavior

Create a clearly run-isolated native DSPy program from immutable definitions. Keep one small supported runtime boundary, removing private compatibility and unused abstractions when behavior tests permit. An optional Jev/ReAnchor experiment must be independently gated and must not block this simplification.

Invariants

  • Runs with different providers/histories cannot mutate one another's predictors or stream attribution.
  • All public events and safe output fields preserve the same contract during the refactor.
  • DSPy callbacks, usage tracking and MLflow callback composition remain active.
  • No generic framework or new private ReAct fork replaces the existing code.
  • Experimental decision types stay internal; authorization remains deterministic.

Implementation slices

A. Cache immutable prompt/spec definitions only; create run-scoped predictor/module instances. Add overlapping-run tests before changing lifetime rules.

B. Characterize supported locked-version termination behavior. Remove the private patch where possible; otherwise isolate a single documented compatibility shim with tests and an explicit removal criterion. Do not silently catch unrelated provider failures as normal partial answers.

C. Inventory YAML dialect uses. Keep real configuration needs; replace unused generality with direct typed Signature/Module composition. A requirements spec does not require a runtime graph language.

D. Optional experiment after the baseline: choose either a decision-typed capability selector or an evidence-sufficiency decision. Keep the old predictor available. Pin experimental behavior and use independent calibration/development and final holdout data.

Contracts and frontend

No frontend DSPy imports or experimental types. Any selected decision is normalized to a plain domain result and the already-approved public schema. Show evidence limitations, not raw model confidence as a truth guarantee.

DSPy evaluation and MLflow

Measure task quality, false-sufficient evidence judgments, invalid output, latency and request/token cost. Log model, dataset, prompt/program, calibration and dependency identities for every experiment. Do not label an unmeasured migration as faster, cheaper or better calibrated.

Official implementation references, checked October 8, 2026: Jev decisions, ReAnchor. These APIs are experimental; verify against the lockfile.

Acceptance tests

  1. Two interleaved runs with different providers and histories retain isolated configuration, streams and usage attribution.
  2. Cancelling one run cannot cancel or contaminate the other.
  3. Streaming and non-streaming paths produce equivalent safe final fields.
  4. Forced/partial/error termination remains correctly normalized with no dependence on unrelated exception wording.
  5. Callback composition still permits opt-in MLflow tracing without making tracing a runtime dependency.
  6. Removed dialect features have no remaining callers; behavior fixtures pass without a second replacement DSL.
  7. An optional decision experiment is activated only after passing the same quality/safety/budget gates on the final holdout.

Non-goals

No broad dependency upgrade, Flex program evolution, always-on critic or simultaneous migration to a new execution framework.
